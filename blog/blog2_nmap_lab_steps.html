A reproducible, step-by-step walkthrough of writing Lua NSE scripts, installing local services, updating Nmap’s script database, and interpreting the results.

Author: Sanjith Madhavan   •   Environment: Ubuntu / Nmap 7.98

Topics: SNMP / UDP 161 · NTP / UDP 123 · Linux terminal · NSE script lifecycle

Purpose of this post: This is the procedure log for the demonstration video. Unlike the first blog, this article focuses on the steps and commands used to create, register, and run the scripts; screenshots are not necessary for this post.

1. Tools and concepts

The lab uses Nmap 7.98, its Nmap Scripting Engine (NSE), Lua, the SNMP daemon (snmpd), and Chrony as the NTP service. SNMP commonly uses UDP port 161; NTP uses UDP port 123. These scripts were developed for a local lab target (127.0.0.1).

The SNMP script checks whether a request using the default community string can retrieve system information. The NTP script sends a legacy Mode 7 monlist probe and reports whether a response is detected. A response needs validation before calling a target vulnerable, and no response does not prove the target is secure.

2. Install the required packages

Update the package list and install the SNMP tools/service and Chrony:

sudo apt update
sudo apt install snmpd snmp chrony -y

Start the services and inspect their status:

sudo systemctl start snmpd
sudo systemctl status snmpd
sudo systemctl start chrony
sudo systemctl status chrony

The service-status command should show Active: active (running) if the daemon started successfully. A running service does not automatically mean every feature or port is exposed.

3. Create the SNMP NSE script

Open a new file in the terminal text editor:

nano snmp-custom.nse

Paste the SNMP Lua source into Nano. The core logic imports shortport and snmp, selects UDP port 161, creates an SNMP helper with the community string public, and requests sysDescr.0 (OID 1.3.6.1.2.1.1.1.0). The script returns a potential-exposure message when the request returns a usable value; otherwise, it reports an inconclusive result.

Save the file by pressing Ctrl+O, then Enter, and exit with Ctrl+X.

4. Create the NTP NSE script

Create the second file:

nano ntp-custom.nse

Paste the NTP Lua source. The script imports shortport and comm, selects UDP port 123, constructs a legacy Mode 7 probe using string.char(), and sends it with comm.exchange(). The request uses a five-second timeout. If a response is received, the script reports its size and recommends validating the packet before confirming monlist exposure.

Save with Ctrl+O, press Enter, and exit with Ctrl+X.

5. Install the scripts into Nmap

Copy both files into Nmap’s script directory and refresh the local script database:

sudo cp snmp-custom.nse /usr/share/nmap/scripts/
sudo cp ntp-custom.nse /usr/share/nmap/scripts/
sudo nmap --script-updatedb

Verify that Nmap recognises each name:

sudo nmap --script-help snmp-custom
sudo nmap --script-help ntp-custom

If the description displayed for a script is not the description expected, inspect the file in /usr/share/nmap/scripts/ to make sure the correct source was copied. Then rerun sudo nmap --script-updatedb.

6. Test the SNMP service

Check service status and verify UDP port 161:

sudo systemctl status snmpd
sudo nmap -sU -p 161 127.0.0.1

Run the custom NSE check against the local machine:

sudo nmap -sU -p 161 --script=snmp-custom.nse 127.0.0.1

In the observed lab run, UDP 161 was open and the custom script printed a finding indicating that community public was accepted. A successful request should be validated against the returned OID value; it is good practice to use “potential exposure” unless the test has confirmed the exact condition being claimed.

161/udp open  snmp
| snmp-custom: VULNERABLE: Default community string "public" accepted.
| Risk: Unauthorized information disclosure (CWE-521).
|_Recommendation: Change the default community string and restrict SNMP access.

7. Configure and test NTP port 123

First check the listener:

sudo ss -lunp | grep :123
sudo nmap -sU -p 123 127.0.0.1

Initially, the lab scan reported 123/udp closed ntp. The script has a rule for UDP port 123, so Nmap does not normally invoke it when the port is reported closed.

To configure Chrony to serve time to the local machine, open the configuration file:

sudo nano /etc/chrony/chrony.conf

Add this directive on a new line:

allow 127.0.0.1

Save and restart Chrony, then verify the socket:

sudo systemctl restart chrony
sudo systemctl status chrony
sudo ss -lunp | grep :123

The observed socket listing showed 0.0.0.0:123, meaning a process was listening on UDP port 123 across IPv4 interfaces. Use the Nmap scan again, then run the script:

sudo nmap -sU -p 123 127.0.0.1
sudo nmap -sU -p 123 --script=ntp-custom.nse 127.0.0.1
Interpretation note: An open UDP/123 port only confirms that a service appears to be listening. It does not prove that the legacy monlist feature is enabled. The custom script’s response must be validated as a real Mode 7 monlist response. If the port is closed, the absence of NSE output is expected because the port rule was not met.

8. Troubleshooting checklist

  • “Failed to resolve 161”: use -p 161 or -p 123 to specify a port. For example, use nmap -sU -p 161 ..., not nmap -sU 161 ....
  • No NSE output: check whether the port is open and whether the script's portrule matches the port and protocol.
  • “Script execution failed”: run with -d and inspect the Lua error and line number. A nil table entry should be checked before indexing it.
  • Script description looks wrong: verify the exact installed file and rerun nmap --script-updatedb.
  • No response: report an inconclusive check rather than declaring the host secure.

10. Conclusion

This procedure demonstrates the full NSE workflow: writing a Lua script, installing local test services, registering the scripts with Nmap, checking the target ports, and interpreting the script output. The SNMP test demonstrates why a default read community can expose system details. The NTP test demonstrates why port availability and vulnerability validation are separate steps.

All commands in this walkthrough are intended for a locally controlled lab or systems for which permission has been granted.
