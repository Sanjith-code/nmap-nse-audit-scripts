A safe localhost walkthrough of three custom Nmap NSE checks for legacy NTP Mode 7 monlist behavior: a basic response check, a validated-response enhancement, and a bounded response-size enhancement.

Author: Sanjith Madhavan  •  Lab: Ubuntu / WSL and Nmap

Topics: NTP / UDP 123 · Nmap Scripting Engine · Lua · CVE-2013-5211

Safety and interpretation: Run these scripts only against your own localhost lab. The repository’s NTP scripts are restricted to loopback. Do not enable legacy Mode 7, expose UDP/123 to the internet, or scan a public time server. A closed UDP/123 port, silence, or timeout is inconclusive; it is not proof that a host is secure. A normal NTP reply does not demonstrate monlist support.

This post complements my SNMP script article with the NTP half of the project. The scripts are for learning how NSE checks are structured and how to interpret limited network evidence. They do not enumerate client addresses or prove vulnerability from silence.

Project files and the complete README are in my Nmap NSE audit scripts repository. It is private, so GitHub access is required.

1. What the three scripts check

  • ntp-custom.nse: sends one legacy monlist request and reports whether a response was received. A response still needs validation.
  • ntp-monlist-enhanced1.nse: checks for the expected Mode 7 response bit, implementation, opcode, and minimum header length. It reads one datagram and does not display client records.
  • ntp-monlist-enhanced2.nse: adds the first reply’s byte count and ratio to the 48-byte request. This single-datagram ratio is a limited indicator, not a full amplification measurement.

A matching legacy reply is a reason to review the server’s version and configuration. Confirming whether CVE-2013-5211 applies requires context beyond one packet.

2. Get the scripts and check the lab tools

After signing in to GitHub and authenticating Git in WSL, clone the private project and enter its folder:

git clone https://github.com/Sanjith-code/nmap-nse-audit-scripts.git
cd nmap-nse-audit-scripts

Install Nmap and Chrony if needed, then record the Nmap version:

sudo apt update
sudo apt install -y nmap chrony
nmap --version

Start the local time service only if you want a normal NTP service available. Chrony does not need legacy monlist enabled for this walkthrough:

sudo systemctl start chrony
sudo systemctl status chrony --no-pager
sudo ss -lunp | grep ':123'
Screenshot needed before publishing: capture the real Chrony service status and local UDP/123 listener. Do not change Chrony to expose the service on a network interface.

3. Confirm Nmap can read the script files

From the repository root, display each script’s help text:

sudo nmap --script-help ./scripts/ntp-custom.nse
sudo nmap --script-help ./scripts/ntp-monlist-enhanced1.nse
sudo nmap --script-help ./scripts/ntp-monlist-enhanced2.nse

If Nmap reports a Lua syntax or script-loading error, stop and fix that before scanning. Do not describe a failed load as a network finding.

Screenshot needed before publishing: capture the Nmap version and the three script-help results in your own terminal. Do not include credentials, tokens, or unrelated private information.

4. Run each check against localhost

Run one script at a time so each result is easy to review and capture. These commands target only IPv4 loopback:

sudo nmap -n -Pn -sU -p 123 --reason --script ./scripts/ntp-custom.nse 127.0.0.1
sudo nmap -n -Pn -sU -p 123 --reason --script ./scripts/ntp-monlist-enhanced1.nse 127.0.0.1
sudo nmap -n -Pn -sU -p 123 --reason --script ./scripts/ntp-monlist-enhanced2.nse 127.0.0.1

Output depends on the local service and network stack. Record exactly what your terminal shows. A closed result, no script output, or a timeout does not establish that monlist is disabled or that the host is secure; it means this check did not obtain a response to validate.

Screenshots needed before publishing: take one genuine terminal capture for each of the three commands above. Keep the target visible as 127.0.0.1. Do not create a positive monlist result by enabling Mode 7.

5. How to read the results

  • A response from the basic check means only that a packet was received; validate it before making a vulnerability claim.
  • A reply rejected by Enhancement 1 did not match the expected header fields. That is not a vulnerability finding.
  • A matching Mode 7 monlist reply is evidence of legacy handling and warrants configuration review. It is not a general measurement of amplification.
  • Enhancement 2 measures one UDP datagram only. It does not count additional response packets or calculate a complete amplification factor.
  • UDP/123 closed, open|filtered, silence, and timeout are inconclusive outcomes.

6. Conclusion

This lab compares a basic NTP response check with two bounded enhancements that validate a Mode 7 header and report limited size information. Its main lesson is to describe what a packet actually demonstrates, keep legacy probing on a controlled loopback target, and treat silence as inconclusive.

All testing described here is for systems I own or have explicit permission to assess. The scripts and localhost commands are available in the project repository (private; GitHub access required).
